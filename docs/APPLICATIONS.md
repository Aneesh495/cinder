# Application integration fixtures

Eight authored applications exercise the normal driver, external libc calls
and file/argument handling. They use eleven C translation units, including
three applications with separate implementation modules.

| Application | Implementation and behavior |
| --- | --- |
| JSON | Recursive ASCII JSON syntax, escapes and Unicode surrogate pairs; container/value/string statistics; 128-level depth limit |
| Word frequency | Dynamic open-addressed FNV hash table, rehashing, ASCII case folding and callback-based lexical sorting |
| Graph | Directed adjacency lists, BFS hop counts and binary-heap Dijkstra distances, duplicate edges, cycles and unreachable vertices |
| Bytecode | Text instruction loader, stack, locals, arithmetic, conditional/unconditional branches, bounded execution and printed results |
| Sort/search | Dynamic integer input, stable merge sort checked against callback `qsort`, lower/upper bounds and a serialized checksum |
| Checksums | Streaming IEEE CRC32 checked against a separate bitwise implementation, Adler32 and FNV-1a on binary input |
| Matrix | Blocked binary64 dense multiplication, edge tiles, exact binary-fraction inputs and independently recomputed cells |
| Records CLI | Separate CSV reader/processing module, dynamic records, grouped aggregates and range selection into output files |

Word frequency, graph and records CLI are multi-TU programs. Their interfaces
include aggregate state and results, dynamic allocation and cleanup; word and
record sorting call Cinder-generated callbacks through libc. These integration
sources are excluded from compiler production accounting.

On Linux x86-64:

```sh
make build
build/cindercc -O2 examples/apps/hash_words.c examples/apps/wordfreq/table.c -o word-frequency
./word-frequency examples/apps/fixtures/word-frequency-prose.in
build/cindercc -O2 examples/apps/cli_multi.c examples/apps/records/records.c -o records
./records group examples/apps/fixtures/records-cli-group.in records.txt
make test-apps
```

`tests/test_applications.py` runs forty frozen inputs: twenty-five valid inputs
and fifteen rejected inputs. Expected stdout, stderr, exit status and output
files are checked byte for byte. Cases cover empty input, rehashing, graph
pressure, JSON depth/surrogates, VM loops and underflow, duplicate sort keys,
binary checksums, partial matrix tiles and preservation of prior CSV output
when parsing fails. Limits are explicit: inputs outside each application's
bounded grammar are rejected. JSON accepts non-ASCII characters through
Unicode escapes; raw non-ASCII input is outside this fixture's profile.

GCC and Clang execute every input at O0/O2. A Clang ASan/UBSan O1 build executes
every input as an additional reference check. Frozen expectations come from
independent Python oracles, including Floyd-Warshall distances, Python stable
sorting and exact integer/fraction matrix calculations. They are generated by
`tools/application_fixtures.py`; `--check` recomputes them without writing.
Reference disagreement or missing sanitizer support fails the workload.

Cinder emits every unit at O0/O2. Linux additionally builds each complete
application through the normal driver. An owned linker shim records and
retains only original ELF objects passed to the system linker driver. Its
argv cannot contain user C. Those objects must match standalone Cinder output
byte for byte. Alternative compiler/assembler delegation through PATH fails.
Every original object has nonempty executable code and retained disassembly.
External FILE/stdio, argv and libc behavior remains outside the IR interpreter
profile and is explicitly ineligible for this corpus. It is never counted as
an interpreter success.

Reports preserve exact source/header/harness/fixture inputs, tool binaries and
versions, original objects, link inputs, argv, input hashes, raw output files
and outcomes. A separate read-only reader reconstructs complete input/mode/tool
coverage and compares raw results with independent frozen expectations.
Missing objects, substituted compilers, changed references, altered exits,
hidden host fallback, incomplete logs and inflated counters must fail even
when their manifests are consistently rehashed. Cross-host compilation and
emulated execution are separate profiles and cannot satisfy the native gate.
These application results do not substitute for the full generated-program,
fuzz, failure-recovery or performance campaigns.
